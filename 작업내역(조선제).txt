  ▷ 5. ★ 그런데 관문에서 걸렸다 — 이 제안은 쓸 수 없다
    문제  위 숫자는 모델을 반사실(counterfactual)로 쓴 결과다. 모델은 "관측된 일정에서"
          전력을 맞히도록 학습됐을 뿐, "일정을 바꾸면 전력이 이렇게 변한다" 를 배운
          적이 없다. 그래서 쓸 자격이 있는지를 먼저 재야 했다
    방법  반사실이 맞으려면 적어도 "조건이 비슷하고 배분만 다른 두 날" 에서 어느 쪽
          피크가 높은지는 맞혀야 한다. 요일 종류·기온(±1.5도)·일 생산 총량(±10%)이
          비슷한 쌍을 모아 실제 순서와 예측 순서가 같은지 봤다.
          예측은 구간 외(시간순 롤링 폴드)로 냈다
    결과  쌍 83개 · 방향 일치 48.2% (40/83) · 단측 이항검정 p = 0.670
          모델이 확신할 때 오히려 더 틀린다
            예측차 >= 0  83쌍  48.2%
            예측차 >= 5  48쌍  45.8%
            예측차 >= 10 16쌍  31.2%
            예측차 >= 15  2쌍   0.0%
    진단  전체로 보면 예측 일 최대와 실제 일 최대의 피어슨이 0.863 이라 잘 맞히는 것
          처럼 보인다. 그 상관이 어디서 오는지 갈라 봤다
            설명변수   실제 일최대와 상관   예측 일최대와 상관
            일생산        +0.841          +0.745
            평일(주말)     -0.849          -0.880
            기온          +0.290          +0.268
          ★ 전부 "일 단위 집계" 다. 재배치는 총량을 그대로 두고 배분만 바꾸는 수단이다.
            그 셋을 매칭으로 고정하면 남는 것이 배분 차이인데, 거기서 동전 던지기였다.
            즉 모델은 배분을 읽지 못한다 → 배분을 바꾸는 제안을 이 모델로 평가할 수 없다
    검정력 한계  쌍이 83개뿐이라 일치 50/83(60.2%) 이상이어야 유의해진다. 60% 미만의
          작은 효과는 이 쌍 수로 잡아낼 수 없다. 그래서 "효과가 없다" 가 아니라
          "있다고 말할 근거가 없다" 가 정확한 서술이다.
          다만 "확신할수록 더 틀린다" 는 패턴은 작은 효과가 숨어 있다는 설명과도 안 맞는다

    "미래 전력을 지우면 is_off 가 바뀐다" 를 누수로 탐지하고 있었다. 내 수정이
    그 탐지를 없애서 테스트가 깨졌다. 지적 자체가 맞았던 것이다.
    테스트는 "바꾸면 여전히 탐지 / 지우면 탐지 안 됨(의도된 수정)" 으로 갈라 고쳤다.

    ★ 그런데 더 중요한 것은 따로 있다 — 검증 구간에서는 누수가 그대로 남는다.
      검증 행은 그 날의 전력이 데이터에 있으므로 is_off 가 여전히 타깃에서 나온다.
      즉 모델이 "오늘 쉬는 날" 을 미리 아는 상태로 평가받고 있다. 크기를 쟀다
        기준 (is_off 포함)                 MAE 6.567 (흔들림 0.194)
        is_off 제거                       MAE 6.698 (흔들림 0.059)
        is_off + day_prod_zero 둘 다 제거   MAE 6.920
      누수의 크기는 0.13 이다. 흔들림 수준이라 결론을 바꾸지 않는다.
      → 모델을 바꾸지 않는다. 대신 보고서에 "is_off 는 타깃에서 유도한 값이라
        검증 수치가 최대 0.13 낙관적일 수 있다" 를 한계로 적는다

  ▷ 정리

             (그 날 MAE 18.95 → 0.92). 7일 이하 구간에서는 실적 있을 때와 예측이 동일
    기록할 것 테스트 구간 8일째부터 정확도 1.3배 악화 (lag168 결측) — 피할 수 없다
             is_off 누수 0.13 — 작지만 보고서에 명시
    ★ 교훈  독스트링이 약속한 조건은 반드시 그 조건으로 한 번 돌려 봐야 한다.

     다른 폴더에서도 도는지 — 마지막 건 내가 적은 안내가 틀려서 고쳤다).

  environment.yml — 버전 고정
    수치를 좌우하는 넷을 고정했다. 버전이 다르면 검증 블록이 어긋난다.
      numpy 2.4.6 · pandas 3.0.6 · scikit-learn 1.9.1 · lightgbm 4.7.0
    ★ libblas=*=*openblas 를 추가했다. 이게 없으면 MKL 이 깔리고 numpy 행렬곱에서
      인터프리터가 오류 없이 죽는다 — [9] 14번에 적힌 바로 그 문제다. 조원이
      환경을 새로 만들면 똑같이 겪는다. conda env create --dry-run 으로 고정
      버전이 해결되고 openblas 빌드로 잡히는 것까지 확인했다.
    ★ 이 파일은 ASCII 로만 쓴다. 윈도우 conda 가 cp949 로 읽어서 한글 주석이
      있으면 디코딩 오류를 낸다 (실제로 겪었다). 한글 설명은 사용법 파일에 둔다.

  조원이 할 일은 네 줄이다
    git pull
    conda env create -f environment.yml
    conda activate kamp-contest
    python "Resource optimization AI.py" --serve

  ※ 이미 kamp-contest 환경이 있는 조원은 버전 고정이 적용되지 않는다.
    conda env remove -n kamp-contest 후 다시 만들거나, 최소한 BLAS 만이라도
    conda install -c conda-forge "libblas=*=*openblas" 를 돌려야 한다.
