==============================================================
 결정 근거 상세 (보고서 작성용)
==============================================================
해당 txt는 보고서 작성시 참고용이며, 프로젝트에서 내린 중대한 선택들의
"상세한 근거"를 모아둔 문서다. 결정의 목록과 상태는 작업내역(최치훈).txt
[★ 결정 사항 기록]에 있고, 이 문서는 그 각 결정에 대해 보고서에 그대로
옮겨 쓸 수 있는 수준의 논거를 붙인 것이다.

작성 기준 (2026-09-30). 수치는 모두 코드 실행 결과 파일에서 가져왔고
출처는 [12]에 적었다. 코드와 이 문서가 어긋나면 코드가 맞다.

  이 문서에서 각 항목은 아래 다섯 칸으로 쓴다.
    선택지   실제로 비교한 대안들 (하나만 놓고 "좋아서 골랐다"는 근거가 아니다)
    판단     무엇을 골랐는가
    근거     수치. 무엇과 무엇을 비교해 얼마나 차이가 났는가
    메커니즘 왜 그런 차이가 나는가 (데이터 성질로 설명. 이게 없으면 우연과 구분 안 됨)
    기각     떨어진 대안을 왜 버렸는가 / 한계와 번복 조건
  필요한 곳에는 [보고서 문장 예] 를 붙였다.

  ※ 성능 수치는 두 기준을 함께 쓴다.
     5 to 9월  = 롤링 폴드 전체 (n=2,092 고유일)
     7 to 9월  = CORE. 테스트 구간과 성격이 같은 구간 (n=1,708). 결론은 이 기준으로 쓴다
     이 구분 자체의 근거는 [1.3] 에 있다.


==============================================================
 [1] 평가 설계 — 모든 성능 주장의 전제
==============================================================
모델 선택 근거를 쓰기 전에 "그 점수를 믿을 수 있는 이유"를 먼저 써야 한다.
이 데이터는 증강 데이터라서 평가 설계를 잘못하면 점수가 실제보다 좋게 나온다.
아래 다섯 항목은 보고서 '데이터 진단'과 '예측 모델' 절 사이를 잇는 부분이다.

  -- [1.1] 랜덤 분할을 쓰지 않은 이유 (D12) ----------------------------
  선택지   1) 무작위 train/test 분할   2) 시간순 롤링 폴드
  판단     2) 시간순 롤링 폴드 (5 to 9월을 차례로 검증월로 두고, 그 이전 전체를 학습)
  근거     257일 중 161일이 24시간 전력곡선이 다른 날과 완전히 동일한 복제일이다
           (45개 그룹, 15분 세부값까지 같은 날이 160일).
           같은 lag168 규칙으로 예측했을 때
             복제일  MAE 11.62
             고유일  MAE 23.63   <- 2배 차이
           즉 복제일을 평가에 섞으면 같은 모델이 절반의 오차로 보인다.
  메커니즘 무작위로 나누면 한 복제 그룹의 어떤 날은 학습, 다른 날은 검증으로
           들어간다. 검증일과 글자 그대로 같은 곡선을 학습에서 이미 본 상태가 되므로
           모델은 '예측'이 아니라 '기억'을 하게 된다. 시계열이라 시간 역행
           (미래로 과거를 맞추는) 문제도 함께 생긴다.
  기각     1)은 점수가 부풀려질 뿐 아니라, 실제 운영(과거로 미래를 맞춘다)과
           조건이 다르므로 현장 적용 근거가 되지 않는다.
  [보고서 문장 예]
    "본 데이터는 257일 중 161일이 전력곡선이 완전히 중복되는 증강 데이터였다.
     동일한 lag168 규칙의 오차가 중복일 11.6, 고유일 23.6으로 2배 차이가 나
     무작위 분할은 중복 곡선의 학습-검증 동시 유입으로 성능을 과대평가한다.
     따라서 검증은 시간순 롤링 폴드로 하고, 평가는 고유일만으로 한정하였다."

  -- [1.2] 평가셋을 설정과 무관하게 고정한 이유 ------------------------
  선택지   1) 각 설정이 자기 기준으로 좋은 행만 평가   2) 모든 설정이 같은 행으로 평가
  판단     2) 평가셋 = 고유일 & train_ok 로 고정 (2,092행, CORE 1,708행).
           학습 행만 설정에 따라 바꾼다.
  근거     학습 행을 줄이는 설정(train_ok_strict, 복제일 제외)은 평가셋도 같이 줄이면
           "쉬운 행만 남겨서 점수가 좋아진" 것과 구분되지 않는다.
           실제로 복제일 학습제외 설정은 5월 폴드가 학습 200행 미만으로 건너뛰어져
           5 to 9월 평가 행이 2,092 에서 1,756 으로 달라졌다. 이 설정은 전체 기준
           MAE 를 직접 비교할 수 없고, 폴드 구성이 같은 CORE(n=1,708) 에서만
           비교가 성립한다.
  메커니즘 MAE 는 평균이므로 분모(행 집합)가 달라지면 값의 의미가 달라진다.
  기각     1)은 설정 간 비교가 성립하지 않는다. model.py 는 평가셋 한 줄
           (va = X[(X.ym==m) & X.train_ok & ~X.is_clone])을 모든 run 이 공유한다.
           행 수가 달라진 설정은 실행 시 경고를 출력하게 해 두었다.

  -- [1.3] 7 to 9월(CORE)을 우선 기준으로 둔 이유 (D22) ----------------
  선택지   1) 5 to 9월 전체 평균   2) 9월을 손대지 않은 홀드아웃으로 보관
           3) 9월도 폴드로 쓰되 판단은 7 to 9월로
  판단     3)
  근거     - 5월 폴드는 학습 구간이 4개월뿐이고 그 대부분이 복제일이다.
             최종 후보 기준 5월 MAE 17.83 / RMSE 32.50 인데
             7·8·9월은 8.19 / 6.50 / 5.39 다.
             5월 336행(16%)이 전체 평균을 8.55 로 끌어올린다 (CORE 6.93).
           - 9월 고유일은 14일(335행)뿐이라 단독 홀드아웃으로는 근거가 약하다.
           - 무엇보다 9월은 이미 여러 실험에서 반복 사용돼 홀드아웃의 성질을 잃었다.
  메커니즘 테스트 구간(9/15 이후로 추정)은 전부 고유일이고 증강이 없는 구간이다.
           7 to 9월이 그와 성격이 같다. 5월은 "학습량 부족 + 복제 편중"이라는
           테스트 구간에 없는 조건이 오차에 섞여 있다.
  기각     1)은 테스트 구간에 존재하지 않는 조건을 결론에 섞는다.
           2)는 이미 성립하지 않는다 (사용 이력).
  한계     ★ 완전히 손대지 않은 검증 구간이 없다. 설정 선택에 CORE 수치를 썼으므로
           CORE 성능에는 선택 편향이 남아 있다. 이 점은 보고서 한계에 명시한다.
  구현     model.py 가 CORE_FOLDS 를 한 번 정의하고 baseline.py, error_analysis.py,
           operational_correction.py 가 import 한다 -> 네 스크립트의 기준이 항상 같다.

  -- [1.4] "차이 있음"의 판정 기준 (시드 흔들림) ------------------------
  선택지   1) 설정 A 가 B 보다 MAE 낮으면 A 가 낫다
           2) 같은 설정을 시드만 바꿔 여러 번 돌려, 차이가 흔들림보다 클 때만 인정
  판단     2) 시드 0·1·2 로 3회 반복. 설정 간 차이 < 시드 표준편차면 "차이 없음"
  근거     실제로 이 기준이 결론을 바꾼 사례가 있다. CORE MAE 기준
             8번  조합(가중치0.3 + 1주앞)   7.15  (흔들림 0.12)
             14번 조합 + 가중치 0.1         7.14  (흔들림 0.20)
           차이 0.01 은 흔들림보다 훨씬 작다 -> MAE 로는 둘을 구분할 수 없다.
           그래서 이 둘은 MAE 가 아니라 다른 지표로 갈랐다 ([4] 참조).
  메커니즘 LightGBM 은 feature_fraction·bagging 에 난수를 쓰므로 같은 데이터로도
           점수가 흔들린다. 흔들림 폭을 모르면 우연을 개선으로 착각한다.
  [보고서 문장 예]
    "모든 설정은 시드 3개로 반복 학습하여 평균과 표준편차를 함께 산출하였고,
     설정 간 성능 차이가 시드 표준편차보다 작은 경우는 유의한 차이로 보지 않았다."

  -- [1.5] 목표선(베이스라인)을 4종으로 둔 이유 ------------------------
  선택지   단순 규칙 없이 모델 점수만 제시 / 단순 규칙 1종과 비교 / 4종과 비교
  판단     4종 비교 후, 지표별 최저값을 목표선으로 삼는다
  근거     고유일 기준 (5 to 9월 -> CORE)
             전체 평균           MAE 52.14 -> 53.21   RMSE 59.39 -> 60.39
             lag24(전일 동시각)  MAE 37.08 -> 34.94   RMSE 62.28 -> 60.56
             lag168(전주 동시각) MAE 23.64 -> 22.92   RMSE 48.32 -> 47.71
             요일x시간 평균      MAE 24.61 -> 24.15   RMSE 35.28 -> 35.06
                                 peakMAE 35.51 -> 35.71
           목표선 = 5 to 9월 MAE 23.6 / RMSE 35.3 / peakMAE 35.5
                    7 to 9월 MAE 22.9 / RMSE 35.1 / peakMAE 35.7
  메커니즘 지표마다 이기는 단순 규칙이 다르다. MAE 는 lag168 이, RMSE·peakMAE 는
           요일x시간 평균이 가장 낮다. lag168 은 대체로 맞지만 휴가 직후처럼
           한 번 틀릴 때 크게 틀려(8월 MAE 42.9) RMSE 가 나쁘다.
           그래서 한 규칙만 목표선으로 쓰면 유리한 지표만 고른 셈이 된다.
  세부     베이스라인도 모델과 같은 학습 행(train_ok_strict)·같은 폴드·같은 평가셋·
           같은 점수 함수를 쓰도록 코드를 맞췄다. 그 결과 목표선이
           RMSE 37.6 -> 35.3, peakMAE 37.1 -> 35.5 로 스스로에게 더 엄격해졌다.
  [보고서 문장 예]
    "비교 기준은 전체 평균, 전일 동시각, 전주 동시각, 요일x시간 평균 4종을 두고
     지표별 최저값을 목표선으로 설정하였다. 목표선과 모델은 학습 행·검증 폴드·
     평가 집합·평가 함수를 공유하므로 차이는 모델 능력에서만 발생한다."


==============================================================
 [2] 모델 선택 — LightGBM vs RandomForest
==============================================================
  선택지   1) LightGBM (objective=l1)   2) RandomForest   (과제 요건: 2종 이상 비교)
  판단     1) LightGBM
  근거     같은 피처(full 36개)·같은 학습 행·같은 폴드·시드 3개 평균
             기준                 CORE MAE   RMSE    peakMAE   흔들림
             LightGBM              9.15      14.11    16.19     0.53
             RandomForest          9.96      18.55    21.13     0.07
             (5 to 9월)  LGBM 10.41 / RMSE 18.36 / peak 16.42
                         RF   10.81 / RMSE 19.87 / peak 21.30
           MAE 차이(0.81)는 작지만 RMSE 차이 4.44, peakMAE 차이 4.94 는 크다.
  메커니즘 단순히 "점수가 좋아서"가 아니라, 차이가 나는 지점이 과제의 핵심과 겹친다.
           1) 결측 처리 방식이 다르다. 이 프로젝트는 D11 에 따라 휴무일·가동중단
              구간의 lag 값을 일부러 결측으로 둔다. 결측 자체가 "직전 주가 휴가였다"는
              정보이기 때문이다. LightGBM 은 결측을 분기 규칙으로 직접 학습하지만,
              RandomForest 는 결측을 못 다뤄 -999 로 채워 넣어야 한다. 채운 값은
              극단값이 되어 분기를 왜곡한다.
           2) 손실함수를 목표 지표에 맞출 수 있다. LightGBM 은 objective='l1' 로
              MAE 를 직접 최소화한다. RandomForest 는 분산(제곱오차) 기준 분할만
              가능하다. 이 데이터에는 증강일·생산기록 누락 의심일 같은 이상값이
              섞여 있어 제곱오차 기준은 그쪽으로 끌려간다.
           3) 피크 구간에서 차이가 가장 크다(peakMAE 16.19 vs 21.13, 30% 차이).
              RandomForest 는 잎 평균을 내는 구조라 상위 5% 같은 꼬리 구간이
              평균 쪽으로 눌린다. 과제 배점이 최대피크 위험조건에 있으므로
              이 구간의 열세는 전체 MAE 차이보다 중요하다.
  기각     RandomForest 는 시드 흔들림이 0.07 로 매우 안정적이라는 장점이 있으나,
           "안정적으로 더 나쁜" 수준이다(모든 지표에서 열세). 학습 시간도 길다.
           단, 대조군으로서 결과를 모두 보존한다 (model_results.csv 의 5번 run).
           -> 두 모델이 같은 결론(복제일 가중치·피처세트의 방향)을 주는지 확인하는
              용도로도 쓸 수 있다.
  한계     하이퍼파라미터를 양쪽 모두 기본값 수준으로 두었다. RandomForest 를
           충분히 튜닝하면 격차가 줄 수 있으나, 결측을 직접 다루지 못하는 구조적
           제약은 튜닝으로 해소되지 않는다.
  [보고서 문장 예]
    "두 모델은 MAE 차이가 0.81에 불과했으나 RMSE 4.44, 피크구간 MAE 4.94의 격차를
     보였다. 이는 (1) 휴무 이력을 의도적 결측으로 표현한 lag 설계를 LightGBM만
     분기 규칙으로 수용할 수 있고, (2) L1 손실로 평가지표를 직접 최소화하며,
     (3) 앙상블 평균 구조상 RandomForest가 상위 5% 피크 구간을 과소평가하기
     때문이다. 과제의 평가 대상이 피크 구간이므로 LightGBM을 최종 모델로 선정하였다."

 [3] 피처 세트 — 피처를 4개 빼니 더 정확해진 이유
==============================================================
  선택지   full(36개, lag24 계열 포함) / h7_full(32개, lag24 계열 4개 제외)
           no_plan(19개) / h7_no_plan(12개)   ※ 생산계획 없는 경우 대비
  판단     최종 후보는 h7_full. 생산계획이 오지 않는 경우의 대안은 no_plan 계열
  근거     CORE MAE (시드 3개 평균)
             full        9.15      h7_full      8.05   (-1.10)
             no_plan    19.93      h7_no_plan  17.51
             복제일 가중치 0.3 적용 시: full 7.82 -> h7_full 7.15
           반대 방향 지표도 같이 적는다: peakMAE 는 full 16.19 -> h7_full 17.35 로
           오히려 나빠진다.
  메커니즘 lag24(전일 같은 시각)는 요일이 바뀌는 경계에서 크게 오도한다.
           토요일 예측 시 lag24 는 금요일(정상 가동) 값을 보므로 오차 82.8,
           lag168 은 지난 토요일을 보므로 오차 12.4 다. 주 5일 공장에서는
           "어제"보다 "지난주 같은 요일"이 더 닮은 날이다. lag24 계열이 들어가면
           모델이 그쪽에 비중을 주면서 요일 패턴이 흐려진다.
  부수효과 이 결과는 예측 시계 설계도 함께 정당화한다. h7 세트는 원래 1주 앞 예측용
           (예측 시점에 lag24 가 존재하지 않아 쓰면 누수)으로 만든 것인데, 하루 앞
           예측에서도 더 정확했다. 따라서 하루 앞·1주 앞 모두 같은 세트로 운영할 수
           있고, 현장에서는 리드타임이 길어져도 성능이 떨어지지 않는다.
  기각     no_plan 계열은 MAE 가 2배 이상이다(17.5 to 20.9). 생산계획 정보가
           전력 예측의 핵심임을 보여주는 대조군으로 남기고, 테스트 데이터에
           생산계획이 포함되지 않을 경우의 대비안으로만 쓴다.
  주의     no_plan 세트에서 is_off(휴무일)를 빼야 한다 -> [5.3] 참조.
           빼기 전 no_plan MAE 13.36 은 부풀려진 값이었고 실제는 25.32 였다.
  한계     peakMAE 가 나빠지는 방향은 미해결이다. 피크 정의(D10)가 확정되면
           MAE 와 peakMAE 중 무엇을 우선할지 다시 정해야 한다.


==============================================================
 [4] 증강 데이터(복제일) 처리 — 제외가 아니라 가중치 하향
==============================================================
  선택지   1) 그대로 학습(keep)  2) 학습 제외(drop)
           3) 가중치 하향(0.05 / 0.1 / 0.3 / 0.5 / 0.7 / 1.0)
  판단     3) 가중치 하향. 최종 후보는 0.3 (0.1 과의 우열은 미결, D07)
  근거     CORE MAE (전부 동일 평가셋 n=1,708)
             그대로 1.0      9.15   <- 13번 run 이 0번과 소수점까지 일치 (구현 검산)
             가중치 0.7      8.62
             가중치 0.5      8.34
             가중치 0.3      7.82
             가중치 0.1      7.31
             가중치 0.05    (조합 기준) 7.74   <- 지나치게 낮추면 다시 나빠짐
             학습 제외      13.96   <- 가장 나쁨
  메커니즘 - 제외가 가장 나쁜 이유: 1 to 4월이 거의 전부 복제일이다. 제외하면 5월
             폴드의 학습 데이터가 200행 미만으로 사라져 폴드가 통째로 빠진다
             (평가 행 2,092 -> 1,756). 증강 데이터도 "전력의 시간 패턴" 자체는
             정상이므로, 버리면 계절·요일 구조를 배울 재료가 없어진다.
           - 가중치 하향이 듣는 이유: 복제일은 전력곡선만 복사되고 생산량·기상은
             원본과 다르다. 그래서 생산량-전력 관계가 어긋난다(상관 0.72 vs 0.79).
             관계 학습에는 방해가 되고 수준 학습에는 도움이 된다 -> 버리지 않고
             비중만 줄이는 것이 이 데이터에 맞는 처리다.
           - 0.05 에서 다시 나빠지는 것은 사실상 제외에 가까워지기 때문이다.
             즉 0.1 부근이 "관계 왜곡은 줄이고 수준 정보는 남기는" 지점이다.
  검산     1.0 설정(13번)이 keep(0번)과 정확히 같은 값을 냈다. 가중치 구현이
           의도대로 동작함을 확인하는 장치로 넣은 run 이다. 이런 자기검증 run 은
           재현성 항목의 근거로 쓸 수 있다.
  0.1 vs 0.3 (미결)   조합 설정 기준 CORE
             8번  h7_full + 0.3 :  MAE 7.15 (흔들림 0.12) / peakMAE 16.54
             14번 h7_full + 0.1 :  MAE 7.14 (흔들림 0.20) / peakMAE 17.85
             10번 full    + 0.1 :  MAE 7.31 / peakMAE 15.28   <- peak 최저
           MAE 차이는 흔들림 이내라 구분 불가([1.4]). peakMAE 로 가르면 결론이
           설정마다 뒤집힌다. 그래서 피크 정의(D10)를 확정한 뒤 결정한다.
           현재 최종 후보는 흔들림이 작고 MAE·peakMAE 가 함께 준수한 8번(0.3)이다.
  기록     2026-09-22 실험(5 to 8월·train_ok·full 32개)에서는 "그대로"가 최선이었다.
           조건이 달라지면 결론이 바뀐 사례이므로, 보고서에는 항상 어떤 폴드·학습
           행·피처 세트에서 나온 수치인지 함께 적는다.


==============================================================
 [5] 학습에 쓸 행 선별 — 왜 지우고, 왜 어떤 것은 남기는가
==============================================================
  -- [5.1] 가동 중단 20행: 학습과 평가 양쪽에서 제외 (D08) --------------
  선택지   그대로 / 학습만 제외 / 학습·평가 모두 제외
  판단     양쪽 모두 제외 (is_stop. 8/28 17시 to 8/29 11시 19행 + 9/8 12시 1행)
  근거     휴무일에도 기저부하 약 23 이 유지되는데 이 구간은 15분 값이 0 이다.
           정전 또는 계측 누락으로 판단된다.
  메커니즘 평가에서 빼는 이유가 따로 있다. 예측 불가능한 행은 어떤 모델이든 똑같이
           크게 틀린다. 모든 설정에 같은 크기의 오차가 더해지면 설정 간 차이가
           희석되어 모델 비교 자체가 흐려진다. 즉 이 제외는 점수를 올리려는 것이
           아니라 비교의 해상도를 지키려는 것이다.

  -- [5.2] 생산기록 누락 의심일 15일: 학습만 제외 (D18) ----------------
  선택지   그대로 / 학습 제외 / 학습·평가 모두 제외
  판단     학습만 제외(train_ok_strict), 평가에는 남긴다
  근거     대상 15일 = 하루 종일 생산량 0 인데 일 최대전력이 기저부하를 크게 넘는 날
           (20210101 0102 0110 0124 0211 0212 0213 0301 0307 0314 0321 0328 0509 0713 0715)
           예: 3/21(일) 생산 0, 일 최대 190
           제외 효과  생산량-전력 상관 0.825 -> 0.862
                      LightGBM MAE 11.10 -> 10.35 (full 기준)
                      조합 설정 기준으로는 CORE 7.15 vs 9.65 (누락일 포함 시 +2.50)
  메커니즘 "생산 0인데 고부하"인 행을 그대로 학습하면 생산량 피처의 기울기가 눌린다.
           모델이 "생산량은 전력을 잘 설명하지 못한다"고 배우게 되므로, 생산일정
           조정으로 피크를 낮추겠다는 과제 목적과 정면으로 어긋난다.
  평가에 남기는 이유   평가셋을 설정에 따라 바꾸지 않는다는 원칙([1.2]) 때문이다.
           학습 행을 줄인 효과와 평가 행을 줄인 효과가 섞이면 개선을 증명할 수 없다.
  발견 경로 처음에는 시간 컬럼까지 손상된 7/13, 7/15 두 날만 발견했다(D14). 손상이
           우연히 눈에 띈 것이었고 같은 성질의 날이 13일 더 있었다. 보고서에는
           "개별 이상치 발견 -> 조건 일반화 -> 전수 탐색"의 흐름으로 쓸 수 있다.
  한계     제외 대상 15일 중 9일이 복제일이다. 복제일 처리(D07)가 확정되면 두 결정이
           겹치는 부분을 다시 계산해야 한다.

  -- [5.3] is_off 는 달력 피처가 아니다 (D17) --------------------------
  선택지   is_off 를 A군(달력, 항상 사용 가능) / B군(생산계획 필요) 중 어디에 둘 것인가
  판단     B군
  근거     제거 후 no_plan 세트 실측 MAE 13.36 -> 25.32
  메커니즘 is_off 의 정의가 "일 최대전력 30 미만"이다. 즉 타깃에서 유도한 값이다.
           달력만으로 예측하는 시나리오에 이 피처가 들어가 있으면, 예측 시점에
           알 수 없는 값(그날의 최대전력)을 쓰는 셈이 된다. 점수는 좋아지지만
           현장에서 재현되지 않는다.
  세부     같은 휴무 정보라도 "지난 휴무 이력"(after_off, off_run_prev,
           days_since_off)은 전날 실적으로 계산되므로 A군에 남겼다. 기준은
           "당일을 보는 값인가, 과거를 보는 값인가"다.
  [보고서 문장 예]
    "휴무 여부 피처는 정의상 당일 최대전력에서 유도되므로, 달력 정보만 사용하는
     시나리오에서는 미래 정보 누수에 해당한다. 제거 후 해당 시나리오의 MAE는
     13.36에서 25.32로 재측정되었고, 이 값을 기대 성능으로 정정하였다."

 [6] 휴무일·공휴일 취급
==============================================================
  -- [6.1] 휴무일을 학습에 포함한 이유 (D09) ---------------------------
  선택지   제외 / 가중치 하향 / 포함 + 플래그
  판단     포함 + 플래그(is_off). 49일, 일 최대전력 30 미만
  근거     경계가 명확하다. 일 최대전력이 30 to 100 사이인 날이 하나도 없다
           (기저 23 / 중부하 105 / 고부하 165 의 3단 구조).
  메커니즘 1) 휴무는 생산계획의 일부다. 예측 시점(전날 24시)에 다음날 휴무 여부는
              공장이 이미 알고 있다. 따라서 "모르는 정보"가 아니라 입력이다.
           2) 정작 문제가 되는 구간은 휴무일 자체가 아니라 그 다음 주다. 휴무 기간의
              값을 lag168 로 참조하면 오염된다. 8월 lag168 MAE 가 42.9 로 무너진
              원인이 하계휴가(7/31 to 8/8) 다음 주였다. -> 휴무일을 버리는 대신
              lag 입력에서 결측 처리하고 "직전 가동일 같은 시각" 피처를 따로 두는
              방식으로 해결했다(D11). 8/9 10시 예: lag168 결측, lag_prev_op =
              7/30 10시 값 188 (실제 182). 8월 고유일 MAE 42.9 -> 8.7
  주의     휴무일을 "일 생산량 0"으로 정의하면 안 된다. 생산 0 인데 최대전력이
           100 을 넘는 날이 15일 있다([5.2]). 정의를 잘못 잡으면 그 15일이
           휴무일로 분류되어 이상치가 정상 라벨을 얻는다.

  -- [6.2] 이 공장은 법정공휴일에 쉬지 않는다 (D19, [제안] 상태) --------
  근거     학습 구간 공휴일 10일 중 실제 휴무는 6/6, 8/15 둘뿐이고 둘 다 일요일이다.
           5/5 생산 2,190 / 5/19 생산 2,990 / 8/16(대체공휴일) 생산 10,238 으로 가동.
  세부     다만 오차분석 결과 공휴일은 "가동"이 아니라 "부분가동"이다.
           법정공휴일 MAE 36.71, bias -35.95(과대예측). 생산은 하되 일찍 끝낸다.
           -> D19 는 반만 맞았다. 보고서에는 "공휴일 = 부분가동일"로 쓰는 것이 정확하다.
  상태     추석(9/20 to 9/22) 가동 여부는 주최 측 확인 사항. 기본 가정은 가동.
           확인되면 피처가 아니라 is_off 를 직접 지정하는 편이 안전하다
           (is_holiday 의 기여도는 36개 피처 중 30위로 낮다).

 [7] 예측 조건과 마감 시각
==============================================================
  -- [7.1] 하루 앞 예측 (D01) ------------------------------------------
  근거     과제 목표가 "생산일정 조정을 통한 피크 저감"이다. 전날에 예측이 나와야
           다음날 일정을 바꿀 수 있다. 예측 정확도 편의가 아니라 의사결정 시점에서

  -- [7.2] 마감 시각을 전날 24시로 한 이유 (D02) ------------------------
  선택지   1) 전날 18시 마감   2) 전날 24시 마감
  판단     2) 전날 24시
  근거     18시 마감이면 다음날 18 to 23시를 예측할 때 lag24 가 예측 시점 이후의
           값(당일 18시 이후 실적)을 가리킨다. 즉 누수다. 이를 피하려면 시간대별로
           사용 가능한 lag 를 다르게 두어야 해서(18시 이후는 lag30 이상만) 피처 구성이
           시간대별로 갈라지고 코드가 복잡해진다.
  메커니즘 24시 마감이면 lag24 이상 모든 값과 전날 일 평균·일 최대까지 전부 사용
           가능하고, 모든 시간대가 같은 피처 정의를 공유한다.
  기각     18시 유지 + 시간대별 lag 제한. 얻는 것(6시간 빠른 통보)보다 잃는 것
           (피처 정의 분기, 누수 위험)이 크다. 전날 밤에 나와도 다음날 일정 조정에는
           충분하다.
  한계     주최 측이 예측 구간·마감 조건을 다르게 공지하면 번복한다.


==============================================================
 [8] 타깃과 피크 정의
==============================================================
  -- [8.1] 타깃 = 시간 평균 (D03, 잠정) --------------------------------
  근거     과제 요구사항이 전력사용량 예측이고, 시간 평균은 15분 값 4개의 평균이라
           단일 15분 값보다 안정적이다(학습이 쉽다).
  보완     요금 기준 피크는 15분 최대일 가능성이 크다. 그래서 시간 평균을 예측한 뒤
           시간대별 환산 계수로 15분 최대를 추정하는 경로를 만들어 두었다
           (outputs/peak_ratio.csv). 환산 오차 7.31 -> 2.86.
           계수 예: 7시 1.30, 17시 1.17, 5·12시 1.15, 그 외 약 1.05
  메커니즘 7시·17시는 교대·가동 시작 시점이라 시간 안에서 부하가 급변한다.
           그래서 그 시각만 15분 최대와 시간 평균의 비가 크다. 계수를 시간대별로
           두는 근거가 여기 있다.

  -- [8.2] 15분 컬럼의 해석 (D20) --------------------------------------
  선택지   A안 = 각 15분 구간의 평균값 / B안 = 15분 시점의 순간값
  판단     A안을 기본, B안은 민감도 분석용으로 함께 구현
  근거     1) 평균 컬럼을 15분 값으로 역산했을 때, 단순 산술평균 가정의 절대오차가
              0.245(100%가 ±0.5 이내)인데 사다리꼴(B안 전제) 가정은 2.172
              (30.6%만 일치) -> A안 정황이 강하다.
           2) 두 해석의 결과 차이가 작다. 순위상관 0.9907, 피크 판정 일치율 98.7%.
  메커니즘 2)가 중요한 근거다. 해석이 틀렸을 때의 손실이 작다는 것을 먼저 보였기

  -- [8.4] 피크를 만드는 것은 생산량이 아니라 기온이다 (2026-09-30 정정) --
  처음 가정  "고부하 시간 = 생산이 몰리는 시간"이므로 생산을 옮기면 피크가 내려간다.
             D16(피크 저감 스케줄링)의 전제였고, 근거는 생산량-전력 상관 0.862 였다.
  실제       조건을 "가동일 안"으로 좁히면 그 관계가 사라진다. 피크 시간은 오히려 생산이 적다.

            일 단위 가동일만              156        0.094           0.366   ★

          두 값이 같이 움직인다. 정작 스케줄링이 건드릴 수 있는 범위(가동일 안의 변동)에서는

  근거 2  시간 단위로 봐도 같다. 7 to 9월 상위 30개 피크 시간 vs 나머지 고부하(135+) 구간
            구분                       n      전력     생산     기온     습도
            상위 30개 피크 시간        30    197.8    1,316   29.0℃    71.7
            나머지 고부하(135+)       470    167.9    1,523   25.7℃    81.6
          전력이 30 높은데 생산은 207 적다. 크게 다른 것은 기온 3.3℃ 뿐이다.

  근거 3  "더운 날이 바쁜 날이었을 뿐" 이라는 반론을 막기 위해 같은 날 안에서 비교해도 같다.
            일 최대가 난 시간          54    186.8    1,281   26.0℃
            같은 날 다른 고부하 시간  446    167.6    1,538   25.8℃
          같은 날, 같은 고부하 상태인데 최대가 나는 시간의 생산량이 257 적다.

  근거 4  생산량은 시간당 800 부근에서 포화한다. 구간별 평균(생산 → 전력)
            85→106.7   296→116.1   504→137.0   706→155.4
            910→164.0  1,104→162.9  1,547→166.0

  한계    냉방 전력이 따로 계량되어 있지 않아 "기온 → 냉방부하 → 피크" 경로를 직접 확인할 수는

     시간대는 오히려 생산량이 낮았으며(1,316 vs 1,523) 기온만 3.3℃ 높았다. 따라서 본
     과제의 피크 위험조건은 생산 집중이 아니라 고온 조건으로 정의하였다."


==============================================================
 [9] 채택하지 않은 것 — 운영규칙 보정 (D23)
==============================================================
이 항목은 "전체 점수가 좋아졌는데도 채택하지 않은" 사례라서, 판단 기준을
세워 두는 것이 왜 필요한지 보여주는 근거로 쓸 수 있다.

  발견     오차분석에서 특정 조건의 오차가 압도적으로 크다.
             마지막 생산시간 이후     n=208  MAE 16.31  bias -12.84 (과대예측)
             공휴일 & 생산종료 이후   n=31   MAE 88.05  bias -88.05 (전량 과대예측)
  규칙     생산계획상 마지막 생산 시각 이후는 예측 전에 알 수 있으므로, 그 구간의
           예측값이 학습구간 동일조건 중앙값(약 23)보다 크면 중앙값으로 자른다.
  결과     5 to 9월  MAE 8.55 -> 7.44,  RMSE 16.16 -> 12.71   (좋아짐)
           7 to 9월  MAE 6.93 -> 6.98,  RMSE 10.58 -> 11.23   (나빠짐) ★
  판단     채택하지 않는다(일괄 적용 기준). 개선이 거의 전부 5월 공휴일 부분가동
           2일(5/5 MAE 71.2, 5/19 MAE 53.8)에서 나온다.
  메커니즘 전체 평균이 좋아진 것은 규칙이 일반적으로 맞아서가 아니라, 오차가 극단적으로
           큰 소수 행을 눌렀기 때문이다. 같은 규칙을 테스트 구간과 성격이 같은
           7 to 9월에 적용하면 정상 가동일의 종업 후 부하까지 잘라내 오차가 늘어난다.
           즉 이 규칙은 "부분가동일 판별"이 필요한데, 현재 규칙에는 그 판별이 없다.
  대안     1) 부분가동일로 판별된 날에만 적용
           2) 자르지 말고 "생산종료 후 경과시간"을 피처로 주어 모델이 스스로 배우게 함
              (후처리보다 피처 쪽이 낫다: 후처리는 폴드마다 상한을 다시 정해야 하고
               규칙과 모델의 책임 경계가 흐려진다)
  [보고서 문장 예]
    "해당 규칙은 전체 구간 MAE를 8.55에서 7.44로 개선하였으나, 개선분이 5월
     공휴일 2일에 집중되어 있었으며 테스트 구간과 성격이 같은 7 to 9월에서는
     6.93에서 6.98로 악화되었다. 따라서 전체 평균 개선을 근거로 채택하지 않고,
     부분가동 여부를 모델이 학습할 수 있는 피처 형태로 전환하는 방향을 택하였다."

 [10] 시드 앙상블 — 같은 모델을 3번 돌려 평균한 이유
==============================================================
  선택지   1) 시드 1개 모델 그대로   2) 시드 3개의 예측값 평균
  판단     2) 최종 후보는 시드 0·1·2 의 예측값을 평균한다
  근거     CORE 기준
             시드별 점수의 평균      MAE 7.15  (흔들림 0.12)
             시드별 예측의 평균      MAE 6.93  RMSE 10.58
           같은 학습 설정인데 0.22 개선된다.
  메커니즘 LightGBM 은 feature_fraction·bagging 난수로 서로 다른 오차를 낸다.
           예측을 평균하면 상관이 낮은 오차 성분이 상쇄된다(분산 감소).
           점수를 평균하는 것과 예측을 평균하는 것은 다르다 — 전자는 흔들림의
           크기를 알기 위한 것이고, 후자는 실제 성능을 얻기 위한 것이다.
           이 문서와 보고서에서 둘을 구분해 적어야 한다.
  부가     LightGBM·RandomForest 를 섞는 방식도 가능하지만 RandomForest 가 모든
           지표에서 열세라 현재는 시드 앙상블만 쓴다. 이종 모델 결합은 RF 쪽
           약점(피크 과소)이 그대로 섞여 들어올 위험이 있다.

 [11] 아직 근거가 부족한 것 (보고서 한계 절에 쓸 내용)
==============================================================
  1. 독립 홀드아웃이 없다. 9월도 실험에 사용했으므로 CORE 성능에는 설정 선택
     편향이 남아 있다. 실제 테스트 성능은 이보다 나쁠 수 있다. -> [1.3] 한계
  2. 피크 구간 과소예측이 구조적으로 남아 있다. 피크 구간 bias +16.02,
     93.1%가 과소예측이다. 평균 오차를 줄이는 L1 목적함수가 꼬리를 평균 쪽으로
     끌어당기는 결과다. 분위수 회귀(0.9) 또는 비대칭 손실로 대응 예정.
  3. 복제일 가중치(0.1 vs 0.3)와 피크 정의(D10)가 서로 묶여 있어 둘 중 하나가
     정해지지 않으면 다른 하나도 확정할 수 없다.
  4. 증강 데이터의 원본을 식별할 수 없다. 복제 그룹 안에서 어느 날이 원본인지
     구분할 방법이 없어 그룹 전체를 복제일로 처리했다(D06). 원본만 남기는
     처리는 불가능하다.
  5. 공휴일·부분가동일의 표본이 적다(법정공휴일 96행, 공휴일&생산종료 후 31행).
     이 구간의 결론은 표본 부족을 함께 밝혀야 한다.
  7. 생산량 컬럼의 기록 시각이 의심스럽다. 가동일 평균으로 19시 생산이 2,365 로 가장 많은데
     전력은 145.9 로 중간이다. 생산 실적이 교대 종료 시점에 몰아서 기록됐을 가능성이 있다.
     시간 단위 생산 스케줄링 모형을 세우기 전에 확인이 필요하다 (주최 측 문의 목록).
  6. lag168 에 대한 의존이 주 단위 편향으로 나타난다. 휴가 직후 주(8/9)는 lag168 이 전부
     결측이라 과소(bias +5.82), 그 다음 주(8/16)는 lag168 이 직전 주를 가리켜 과대
     (bias -8.18)다. 8/16 주 예측은 1주 전 실적과 상관 0.972 로, 사실상 "지난주 복사"에
     가까웠다. 상세는 작업내역(최치훈).txt [13] 추가 발견.
