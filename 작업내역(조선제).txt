==============================================================
 데이터셋·전처리 정리 (팀 공유용)
 과제: ⑤ 제조 생산데이터 기반 전력사용량 예측 및 최대피크 위험조건 분석
 기준일: 2026-09-23
 범위: 파일별 역할 / 기존 전처리 점검 / 보강 내용과 검증 / 데이터 특성 /
       상관관계와 예측 가능성의 근거 / 모델 코드 설명 / 1차 비교 실험 결과
 관련 문서: 작업내역.txt (결정사항 D01 to D19), 피처목록.txt (피처 우선순위)
==============================================================

■ 세 줄 요약
  1. 팀원이 만든 전처리(preprocess.py)는 구조가 탄탄하다. 복제일·휴무일·가동중단
     판별과 "load() 단일 입구" 설계는 그대로 간다.
  2. 보강한 핵심은 두 가지다.
     ① 생산 기록 누락일을 2일 → 15일로 넓혀 탐지 (train_ok_strict)
     ② 당일 휴무 플래그(is_off)를 달력 전용 피처 세트에서 뺌 (누수성 모순 제거)
  3. 그 결과 성능 수치가 바뀌었다. 생산계획을 받는 시나리오는 MAE 11.13 → 10.35로
     좋아졌고, 달력만 쓰는 시나리오는 13.36 → 21.56으로 "나빠졌다".
     후자는 성능 하락이 아니라 원래 부풀려져 있던 값이 제자리를 찾은 것이다.

  ▷ 데이터

  ▷ 코드 (src/) — 실행 순서대로
    preprocess.py   ★ 모든 단계의 단일 입구.
        원본을 읽어 정제하고 "이 행을 학습에 써도 되는가"를 판단하는 플래그를 붙인다.
        다른 스크립트는 전부 여기의 load() 를 호출한다. 전처리 규칙이 한 곳에만
        있어야 분석·학습·평가가 서로 어긋나지 않기 때문이다.

    eda.py          EDA 그림 7장 생성 → outputs/eda/01 to 07.png

    eda3.py         기저부하 구조와 피크 조건을 숫자로 출력 (그림 없이 콘솔)
        "생산량 0인데 전력을 쓰는 시간"을 파고드는 용도.

    pattern.py      날짜별 24시간 전력곡선에 패턴 ID를 부여 → outputs/daily_pattern.csv
        같은 곡선이 몇 번 반복되는지 = 증강 복제의 규모를 재는 도구.

    baseline.py     베이스라인 4종을 시간순 롤링 폴드로 평가 → outputs/baseline_results.csv
        모델이 넘어야 할 기준선. 이걸 못 이기면 모델을 쓸 이유가 없다.

    features.py     모델 입력 피처 생성 → outputs/features.csv, outputs/peak_ratio.csv
        피처목록.txt 의 A to D 분류를 코드로 옮긴 것. 예측 시점에 알 수 있는
        정보만 쓰도록 lag 24 이상만 참조한다.

    model.py        예측 모델 학습·비교 → outputs/model_results.csv
        LightGBM / RandomForest 를 시간순 롤링 폴드로 평가한다. 자세한 설명은 [8].

    __init__.py     src 를 패키지로 인식시키기 위한 빈 파일.

  휴무일 판별           일 최대전력 30 미만 = is_off (49일)          D09

  복제일 판별           24시간 전력곡선이 다른 날과 완전히 같은 날    D06

  ▷ 이 설계에서 특히 잘 된 점
    - load() 단일 입구: 전처리 규칙이 한 곳에만 있어 분석과 학습이 어긋나지 않는다.
    - 복제일 분리: 증강 데이터를 걸러내지 않으면 성능이 2배 좋게 보인다.
      (lag168 베이스라인 MAE 복제일 11.6 vs 고유일 23.6)
    - lag 입력에서 휴무·중단 값을 결측 처리(D11): 휴가 다음 주 lag168 오염을 막는다.

  ----------------------------------------------------------------
  보강 1. 생산 기록 누락일 탐지를 2일 → 15일로 확대   [preprocess.py]
  ----------------------------------------------------------------
  문제
      기존에는 7/13, 7/15 만 제외 대상이었다(is_corrupt). 그런데 이 이틀은
      "시간 컬럼까지 같이 손상돼서" 우연히 눈에 띈 것이지, 생산 기록 누락의
      전체 목록이 아니다.
  발견
      "하루 종일 생산량이 0인데 일 최대전력이 기저부하를 한참 넘는 날"을
      기준으로 다시 세면 15일이 나온다 (복제일 9 / 고유일 6).
        20210101 20210102 20210110 20210124 20210211 20210212 20210213
        20210301 20210307 20210314 20210321 20210328 20210509 20210713 20210715
      예) 3/21(일) 생산량 0인데 일 최대 190, 3/28(일) 생산량 0인데 185.
      7/13, 7/15 와 성격이 같은데 시간 컬럼이 멀쩡해서 안 걸렸던 날들이다.
  왜 문제인가
      이런 행을 그대로 학습하면 모델이 "생산 0인데 고부하"를 배워서
      생산량 피처의 기울기가 눌린다.
  처리
      is_prod_missing 플래그 추가.
      train_ok_strict = train_ok & ~is_prod_missing  (6,100행 → 5,788행)
      ※ 기존 train_ok 는 건드리지 않았다. 기존 결과와 비교할 수 있어야 하고,
        무엇을 제외할지는 팀이 정할 문제이기 때문이다.
  효과 (측정값은 [4] 참고)
      생산량-전력 스피어만 상관   0.825 → 0.862
      LightGBM MAE (full 세트)   11.10 → 10.35

  ----------------------------------------------------------------
  보강 2. is_off 를 달력 세트에서 제거 (누수성 모순)   [features.py]
  ----------------------------------------------------------------
  문제
      is_off 는 "일 최대전력 30 미만"으로 정의된다. 즉 타깃에서 유도한 값이라
      예측 시점에는 알 수 없다. 팀 합의는 "생산계획으로 알 수 있다고 가정"(D09)인데,
      그렇다면 is_off 는 생산계획을 받는 시나리오에서만 쓸 수 있다.
      그런데 기존 코드에서 is_off 는 A군(달력)에 들어 있었고,
      A군은 "생산계획이 없는 시나리오"용 세트(no_plan)에 그대로 포함된다.
      → 생산계획 없이 쓰는 세트가 생산계획이 있어야 아는 값을 쓰고 있었다.
  처리
      is_off 를 A군 → B군(생산계획)으로 이동.
      단, after_off / off_run_prev / days_since_off 는 "지난 휴무 이력"이라
      전날 실적으로 알 수 있으므로 A군에 남긴다. 과거를 보는 값과
      당일을 보는 값을 가른 것이 핵심이다.
  효과
      no_plan 세트 MAE 13.36 → 25.32.
      ★ 이건 성능이 나빠진 게 아니라, 13.36 이라는 숫자가 애초에
        타깃 유래 정보로 부풀려져 있었다는 뜻이다. 25.32 가 실체다.
        팀이 "달력만 있어도 MAE 13 나온다"고 믿고 있으면 오판이 된다.

  ----------------------------------------------------------------
  보강 3. 휴무 이력 피처 3종 추가   [features.py]
  ----------------------------------------------------------------
  근거
      기존 after_off 는 0/1 이라 "어제 하루 쉬었다"와 "9일 하계휴가 뒤 복귀"를
      구분하지 못한다. 실제로 복귀일 부하는 다르다.
        직전 휴무 0일(평상시) 일 최대 평균 165.2
        직전 휴무 1일          182.2
        직전 휴무 9일(하계휴가) 193.0
  추가 피처
      off_run_prev     직전 연속 휴무 길이 (하계휴가 복귀일이면 9)
      days_since_off   마지막 휴무 이후 경과일
      is_holiday       법정공휴일 여부 (2021 달력, 대체공휴일 포함)
  효과
      no_plan 세트 MAE 25.32 → 23.19 (-8.4%)
      full 세트에서는 기여가 작다. 생산계획이 있으면 그쪽이 더 강하기 때문.
      ※ 9일 휴가는 학습 구간에 1번뿐이라 통계적 근거는 약하다. 표본이 늘면 재확인할 것.

  ----------------------------------------------------------------
  보강 4. day_prod_zero — is_off 의 누수 없는 대체값   [features.py]
  ----------------------------------------------------------------
  발견
      휴무일 49일은 100% 전부 일 생산량이 0이다 (포함관계 확인).
      → 생산계획만 받으면 휴무일 후보를 타깃 없이 만들 수 있다.
      단 역은 성립하지 않는다. 일 생산량 0인 64일 중 15일은 고부하다
      (= 보강 1의 생산 기록 누락 의심일). 일치율 93.75%,
      보강 1로 그 15일을 빼면 일치율이 100%가 된다.

  ----------------------------------------------------------------
  보강 5. 공휴일 실태 확인 — 이 공장은 법정공휴일에 쉬지 않는다   [preprocess.py]
  ----------------------------------------------------------------
  확인 결과 (학습 구간 내 공휴일 10일)
      날짜        공휴일        휴무?   일최대   일생산량

      2021-02-11  설연휴        가동     168         0   (복제일)

      2021-02-13  설연휴        가동     109         0   (복제일)
      2021-03-01  삼일절        가동     179         0   (복제일)
      2021-05-05  어린이날      가동     112     2,190

      2021-08-15  광복절        휴무      23         0   ← 일요일
      2021-08-16  대체공휴일    가동     183    10,238  ← 연중 최대급 생산
  해석
      실제로 쉰 공휴일 2일은 둘 다 일요일이다. 즉 "공휴일이라서" 쉰 날은 0일이다.
      5/5, 5/19, 8/16 은 생산량까지 많은 정상 가동일이다.
  시사점 ★
      테스트 구간에 추석(9/20 to 22)이 포함되더라도 이 공장은 가동할 가능성이 높다.
      작업내역 D09 의 "추석이 포함될 가능성 → 모델이 휴무를 배워야 함"은
      전제를 다시 볼 필요가 있다. 실제 조업 중단은 하계휴가(7/31 to 8/8)처럼
      회사 자체 휴무로만 나타난다.
      is_holiday 를 피처로 넣어는 뒀지만 기여도는 낮다(전체 36개 중 30위).
      주최 측이 추석 휴무 여부를 알려주면 피처가 아니라 is_off 를 직접
      지정하는 쪽이 안전하다.

  ----------------------------------------------------------------
  보강 6. 데이터 무결성 검증 추가   [preprocess.py]
  ----------------------------------------------------------------
      lag 피처는 shift(24), shift(168) 처럼 "1행 = 1시간, 누락 없이 연속"을
      전제한다. 이 전제가 깨지면 예외가 아니라 조용히 틀린 lag 가 만들어진다.
      → 하루 24행인지, dt 간격이 1시간인지 assert 로 막았다.
      테스트 데이터를 이어 붙일 때 특히 중요하다.

  ----------------------------------------------------------------
  보강 7. 피크 환산 계수 산출 → outputs/peak_ratio.csv   [features.py]
  ----------------------------------------------------------------
      시각별 (15분 최대 / 시간 평균) 평균 비율.
        7시 1.30 · 17시 1.17 · 5시 1.15 · 12시 1.15 · 나머지 약 1.05
      교대 전환 시각에 값이 크다. 시간 평균을 예측하고 이 계수로 곱해
      요금 기준 피크(15분 최대)를 환산하는 2단계 구조에 쓴다.
      서브 개발자의 피크 분석·스케줄링 입력이다.

 [5] 데이터셋은 어떤 성격인가
==============================================================

  ▷ 규모와 구조
      2021-01-01 to 09-14, 시간 단위 6,168행 = 257일 x 24시간. 시간 누락 없음.
      컬럼 18개: 전력(15/30/45/60분·평균), 생산량, 공장인원, 인건비,
                 전기요금(계절), 기상 4종(기온·풍속·습도·강수량), 달력 3종(day/d/m)
      평균 = 15분 값 4개의 산술평균(반올림)임을 확인했다.
             따라서 15분 최대 >= 시간 평균이 항상 성립한다.

  ▷ 성격 1. 절반 이상이 증강 복제 데이터 ★ 가장 중요
      257일 중 161일(63%)은 24시간 전력곡선이 다른 날과 완전히 같다.
      1 to 6월에 몰려 있고 7 to 9월은 거의 전부 고유일이다.
      전력만 복사되고 생산량·기상은 복사되지 않아서, 복제일에는
      "생산은 많은데 전력은 평탄" 같은 모순된 행이 섞여 있다.
      → 랜덤 분할 금지(같은 곡선이 학습·검증에 동시 진입).
      → 실제 예측력은 고유일(7 to 9월) 성적으로만 판단한다.

  ▷ 성격 2. 전력이 연속값이라기보다 세 덩어리
      기저부하 약 22 (무가동, 공조·조명 등) / 중부하 약 105 / 고부하 약 165
      가동일 전력 분위수: 10% 23 · 25% 93 · 50% 112 · 75% 155 · 90% 171
      → 회귀 정확도보다 "가동 상태 전환"을 맞히는 게 성능을 가른다.

  ▷ 성격 3. 요일·시각 구조가 강하다
      평일 평균 103 to 123 / 토 51 / 일 41
      평일 8 to 11시, 13 to 19시 고부하, 12시 점심에 하락
      화 to 토 새벽 1 to 6시에도 약 90 (야간 가동), 월요일 새벽은 기저부하
      토요일은 새벽 1 to 6시만 가동하고 8시 이후 기저부하

  ▷ 성격 4. 품질 이슈가 여러 겹
      시간 컬럼 손상   7/13, 7/15 (48행)
      생산 기록 누락   15일 (보강 1에서 확대 탐지)
      가동 중단        20행 (8/28 17시 to 8/29 11시 + 9/8 12시). 휴무일에도 유지되는
                       기저부하 22 가 0이라 정전·계측 누락으로 본다
      결측             풍속 3 / 강수량 1 / 공장인원 17 (소량)
      휴무일           49일 (일요일 29 + 하계휴가 7/31 to 8/8 등)
      중복             날짜+시간 중복 없음

  ▷ 성격 5. 휴무일 경계가 뚜렷하다
      일 최대전력이 30 미만인 날의 최대값 26, 30 이상인 날의 최소값 97.
      26과 97 사이가 비어 있어 임계 30은 어디에 두어도 결과가 같다.

  ▷ 성격 6. 학습 구간에 없는 조건이 테스트에 나올 수 있다
      학습은 9/14까지다. 테스트가 9/15 이후라면
        - 추석(9/20 to 22): 학습 구간에 추석 사례가 없다
        - 9월은 전기요금 계절이 167.2로 바뀐다 (6 to 8월 191.6)
        - 9월 고유일은 14일뿐이라 가을 패턴 표본이 적다


==============================================================
 [6] 무엇과 무엇이 연결되어 있기에 전력을 예측할 수 있나
==============================================================
  ※ 아래 상관은 모두 스피어만(순위 상관), 고유일 + train_ok_strict 기준이다.
    복제일을 섞으면 관계가 흐려지므로 반드시 분리해서 본다.

  ----------------------------------------------------------------
  (1) 생산량 — 가장 강한 설명 변수
  ----------------------------------------------------------------
      생산량 ~ 전력   0.862      공장인원 ~ 전력  0.834
      ※ 생산량과 공장인원은 서로 0.99 로 사실상 같은 변수다. 둘 다 넣으면
        SHAP 중요도가 둘로 나뉘어 해석이 흐려진다. 하나만 쓰는 게 낫다.

      단 관계가 직선이 아니다. 생산량이 늘수록 전력도 늘지만 약 1,000 부근에서 포화된다.
        생산량 구간(고유일 가동시간)   평균 전력
          1 to 73                        104.2
          73 to 204                      106.6
          204 to 506                     117.5
          506 to 972                     149.7
          972 to 1,618                   162.2
          1,618 초과                     158.0   ← 더 만들어도 전력이 안 오른다
      → 그래서 prod_cap(800 상한)·prod_log 같은 포화 반영 피처가 원본 생산량보다
        상관이 높다 (prod_cap 0.867).
      → 피크 저감 관점에서 중요하다. 고부하 구간이 오히려 생산 단위당 전력이
        적으므로, 전체를 낮추기보다 맨 윗부분만 깎는 쪽이 유리하다 (D16).

  ----------------------------------------------------------------
  (2) 기온 — 가동 중일 때만, 그리고 생산량과 함께 작용한다
  ----------------------------------------------------------------
      전체 상관은 0.02 로 거의 없다. 가동·무가동이 섞여 효과가 가려지기 때문이다.
      생산량 구간을 고정하고 기온 구간별 평균 전력을 보면 관계가 드러난다.

        생산량 구간      ~22°C   22 to 26°C   26°C+     차이
        생산 0            47.0      37.9       40.4     없음
        저(1 to 300)     103.2     106.8      118.1     +14.9
        중(300 to 900)   118.9     137.6      163.2     +44.3
        고(900+)         144.3     159.2      171.6     +27.3

      해석
        - 생산 0(무가동)일 때는 기온 효과가 없다 → 건물 냉방이 아니라
          설비 가동에 수반되는 냉방으로 보인다.
        - 생산량이 많을수록 기온의 추가 효과가 크다 → 기온과 생산량은
          더해지는 게 아니라 곱해지는 관계다.
      → 팀원의 "22°C 이상에서 전력 상승" 결론은 확인됐고, 여기에
        "가동 중일 때만, 생산량과 상호작용" 조건이 붙는다.
      → cool(= max(0, 기온-22)) 을 단독으로 넣는 것보다 생산량과의
        상호작용을 모델이 잡도록 하는 편이 낫다. 트리 모델은 자동으로 잡지만,
        선형 모델을 쓸 경우 곱셈 항을 명시적으로 넣어야 한다.

  ----------------------------------------------------------------
  (3) 과거 전력 (lag) — 요일 주기가 하루 주기보다 강하다
  ----------------------------------------------------------------
      자기상관 (작업내역 [5] 기준)
        1시간 전 0.90 / 1일 전 0.37 / 1주 전 0.74
      → "어제 같은 시각"보다 "지난주 같은 요일·시각"이 훨씬 유효하다.
        공장이 요일 단위로 운영되기 때문이다.
      피처 상관
        lag_week_mean4 (최근 4주 같은 요일·시각 평균)  0.737
        lag336 (2주 전)                                0.731
        lag168 (1주 전)                                0.656
        lag24  (1일 전)                                0.535
      → 단일 lag168 보다 최근 4주 평균이 더 안정적이다. 노이즈가 줄기 때문.
      주의: lag 계열은 휴무·중단 값을 결측 처리하므로 결측률이 높다
            (lag168 21.6%, lag336 23.9%). lag_prev_op(직전 가동일 같은 시각)는
            휴무를 건너뛰어 참조하므로 결측률이 0.4% 로 낮다.
            8월 lag168 붕괴(MAE 42.9)는 휴가 다음 주가 휴가 기간을 참조해서 생긴 일이다.

  ----------------------------------------------------------------
  (4) 달력 — 생산계획을 대신하는 정보
  ----------------------------------------------------------------
      is_weekend ~ 전력  -0.569
      is_off     ~ 전력  -0.610   (단 타깃 유래. 생산계획이 있을 때만 사용)
      day_prod_zero      -0.610   (생산계획만으로 만드는 누수 없는 대체값)
      인건비             -0.234   (= 9 to 17시 여부를 뒤집은 값. 시각에서 그대로 나옴)
      전기요금(계절)     -0.032   (월로 완전히 결정됨 → month 와 중복, 제외 가능)

  ----------------------------------------------------------------
  (5) 그래서 왜 예측이 가능한가 — 한 문단 정리
  ----------------------------------------------------------------
      이 공장의 전력은 "얼마나 만드느냐"가 대부분을 결정하고(상관 0.86),
      거기에 "얼마나 더우냐"가 가동 중일 때만 얹힌다(생산량 구간 내 최대 +44).
      그리고 생산 자체가 요일 단위로 반복되기 때문에(1주 자기상관 0.74),
      생산계획을 모르더라도 지난주 같은 요일·시각 값으로 상당 부분을 복원할 수 있다.
      따라서 두 갈래가 성립한다.
        생산계획을 받으면 → 생산량 중심으로 예측 (MAE 약 10)
        달력만 있으면    → 지난주 같은 요일 패턴 중심으로 예측 (MAE 약 22)
      예측이 깨지는 지점은 이 규칙이 안 통하는 곳이다.
      즉 휴무 전후, 생산 0인데 전력을 쓰는 시간, 교대 전환 시각(7·12·17시)이며
      이 세 가지가 "예측오차가 큰 생산조건" 분석(과제 요구사항 ②)의 후보다.

  ----------------------------------------------------------------
  (6) 피크는 생산량만으로 설명되지 않는다
  ----------------------------------------------------------------
      피크 시 평균: 생산량 1,158 · 기온 20.6   (비피크 426 · 15.6)
      그런데 생산량 상위 10% 시간의 86.7% 는 피크가 아니다.
      → 생산량 단독이 아니라 설비 동시가동·기온이 겹치는 조합 조건이 피크를 만든다.
        서브 개발자의 "피크 위험조건" 분석은 단일 변수 임계가 아니라
        조합 규칙으로 접근해야 한다.
      요금 기준 피크는 15분 최대다(한국 최대수요전력 기준).
      시간 평균과의 차이는 평균 7.3이고 7시·17시·12시에 특히 크다.
      → outputs/peak_ratio.csv 의 시각별 계수로 환산한다.

  8-1. 이 문제를 어떻게 푸는가 — 시계열이 아니라 표(table) 회귀다
  ----------------------------------------------------------------
      전력 예측이라 하면 ARIMA·LSTM 을 떠올리기 쉽지만, 이 문제는 지도학습 회귀로
      바꿔서 푼다. 핵심은 "과거 정보를 X 의 열로 집어넣는 것"이다.

        한 행 = 한 시간
        X = 그 시각을 예측할 때 이미 알고 있는 정보 36개 (lag168, 생산계획, 기온 ...)
        y = 그 시각의 전력 (target)

      예) 9/20 14시를 예측할 때, 일주일 전 9/13 14시의 전력값을 lag168 이라는
          열 하나로 넣는다. 그러면 시간 순서 개념이 사라지고 평범한 회귀가 된다.
      이 변환은 features.py 가 이미 끝냈다. model.py 는 그 결과를 받아 쓸 뿐이다.

  ----------------------------------------------------------------
  8-2. 함수 구성
  ----------------------------------------------------------------
      make_model(name, seed)
          모델 1종을 만들어 돌려준다. 현재 lgbm(LightGBM), rf(RandomForest).
          새 모델은 여기에만 추가하면 나머지 코드는 건드릴 필요가 없다.

      rolling_eval(X, cols, model, train_flag, clone, seed)   ★ 핵심
          시간순 롤링 폴드로 학습·예측한 결과를 행 단위로 돌려준다.
          여기만 정확하면 나머지는 자유롭게 바꿔도 안전하다.

      score(s)
          MAE / RMSE / peakMAE / n 계산. baseline.py 와 같은 정의라 직접 비교된다.

      run_all(X, runs, base, seeds)
          설정 여러 개를 시드별로 돌려 폴드별 + 합산(ALL) 성적표를 만든다.

  ----------------------------------------------------------------
  8-3. 검증 규약 — 왜 랜덤 분할을 쓰면 안 되는가
  ----------------------------------------------------------------
      보통 쓰는 train_test_split / KFold 를 이 데이터에 쓰면 점수가 크게 부풀려진다.
      이유가 두 가지다.
        1) 미래로 학습해서 과거를 맞히게 된다. 현실에서 불가능한 일이라 무의미하다.
        2) 복제일 161일 때문에 같은 전력곡선이 학습셋과 검증셋에 동시에 들어간다.
           모델이 답을 외운 것을 실력으로 착각하게 된다.
           (lag168 베이스라인이 복제일 MAE 11.6 vs 고유일 23.6 으로 2배 차이)

      그래서 시간순 롤링 폴드를 쓴다 (D12). baseline.py 와 완전히 같은 규약이다.
        5월 검증 <- 1 to 4월 학습 / 6월 검증 <- 1 to 5월 학습 / ... / 9월 검증 <- 1 to 8월 학습

      ★ 평가셋은 어떤 설정을 주어도 항상 "고유일 & train_ok" 로 고정된다.
        학습 조건을 바꿀 때마다 평가 기준까지 흔들리면 비교 자체가 성립하지 않는다.

  ----------------------------------------------------------------
  8-4. 실험 손잡이 4개
  ----------------------------------------------------------------
      BASE 를 기준으로 각 run 이 "한 가지만" 덮어쓰는 구조다.
      두 가지를 동시에 바꾸면 무엇 때문에 좋아졌는지 알 수 없다.

        cols        FEATURES 의 full (36개) / no_plan (19개)
        model       lgbm / rf
        train_flag  train_ok / train_ok_strict                      (D18)
        clone       keep 그대로 / drop 학습 제외 / weight 가중치 하향  (D07)

  ----------------------------------------------------------------
  8-5. 시드를 3개 돌리는 이유
  ----------------------------------------------------------------
      LightGBM 은 bagging·feature_fraction 때문에 같은 설정이어도 실행할 때마다
      결과가 조금씩 다르다. 한 번만 돌리면 우연히 좋게 나온 값을 실력으로 착각한다.
      그래서 SEEDS = (0, 1, 2) 로 세 번 돌려 평균과 표준편차(흔들림)를 함께 낸다.

      ★ 판단 기준: "기준대비" 차이가 "흔들림"보다 작으면 차이 없다고 본다.

  ----------------------------------------------------------------
  8-6. 함정: 폴드가 건너뛰어지면 비교가 성립하지 않는다
  ----------------------------------------------------------------
      학습 행이 200행 미만이면 그 폴드를 건너뛴다. 이때 평가 행 수(n)가 달라져
      다른 설정과 MAE 를 직접 비교할 수 없게 된다.
      실제로 복제일 학습 제외 설정에서 이 일이 일어났다 ([9] 1번 참고).
      코드가 이 경우를 자동으로 감지해 경고를 출력한다.
