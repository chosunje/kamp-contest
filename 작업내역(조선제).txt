 [2] 파일 구조와 실행 방법
==============================================================

 전체 실행   python run_all.py          15단계, 약 9분
 단계별      python src/<스크립트>.py    어느 폴더에서 실행해도 경로는 저장소 기준

 ── 파이프라인 15단계 ──
   1  preprocess.py        원자료 읽기·정제·플래그 생성
   2  eda.py               EDA 그림 7종
   3  eda3.py              기저부하·피크 통계
   4  pattern.py           날짜별 전력곡선 패턴
   5  features.py          피처 생성 → outputs/features.csv
   6  baseline.py          베이스라인 4종 (모델이 넘어야 할 목표선)
   7  model.py             설정 비교 실험 → model_results.csv
   8  error_analysis.py    조건별 오차 분석 (팀원 작성)
   9  shap_analysis.py     영향요인 SHAP                        ← 내가 추가
   10 peak_driver.py       최대피크 위험조건 분석               ← 내가 추가
   11 peak_alarm.py        피크 경보 검증                       ← 내가 추가
   12 viz_perf.py          성능 체감 그림 (팀원 작성)
   13 forecast.py          1주 앞 예측 + 피크 경보
   14 predict_test.py      테스트 구간 예측 파일 생성           ← 내가 추가
   15 report_final.py      최종 성능 한 장 요약 그림            ← 내가 추가

 ── 파이프라인에 없는 것 (따로 실행) ──
   python src/model.py --fix              약점 공략 실험 28개 (약 12분)
   python src/operational_correction.py   D23 운영규칙 실험 (팀원 작성)
   python src/predict_test.py 20210915 20210930            제출 파일 생성
   python src/predict_test.py 20210915 20210930 --no-plan  생산계획이 없을 때

 ── 내가 만든 스크립트가 하는 일 ──
   shap_analysis.py   어떤 피처가 예측을 만들었나. 피처군(A 달력/B 생산계획/
                      C 기상/D 과거전력)별 합계도 낸다
   peak_driver.py     피크를 만드는 것이 생산량인가 기온인가. 기준 16개를 한꺼번에
                      내서 "기준에 따라 답이 갈린다" 는 것까지 보인다
   peak_alarm.py      경보의 정밀도·재현율. "몇 시" 를 맞힐 수 있는지도 검증
   predict_test.py    제출용. 여러 날을 한 번에, 실적이 없어도 돌아간다

 ── 산출물 위치 ──
   outputs/model_results.csv          설정별 성적표 (CORE 행 포함)
   outputs/model_results_fix.csv      약점 공략 실험 28개
   outputs/error_*.csv                조건별·날짜별 오차 (팀원)
   outputs/shap_importance.csv        피처별 SHAP 기여도
   outputs/shap_by_group.csv          피처군별 합계
   outputs/peak_driver_*.csv          상관·시간대비교·포화·일최대시각
   outputs/peak_alarm_eval.csv        경보 정밀도/재현율
   outputs/peak_alarm_days.csv        일 단위 경보표 (현장이 받는 형태)
   outputs/submission_*.csv           제출용 예측
   outputs/perf/                      성능 체감 그림 6종 (팀원)
   outputs/eda/                       EDA 그림 7종

 [3] 데이터가 어떻게 생겼나
==============================================================

 규모     6,168행 = 257일 x 24시간. 1시간 간격으로 빠짐없이 연속
 기간     2021-01-01 to 2021-09-14
 타깃     시간 평균 전력 (target). 15분 단위 컬럼 4개는 피크·요금용

 ── 가장 중요한 특성: 절반 이상이 복제된 날이다 ──
   복제일 161일 / 고유일 96일
   "다른 달의 같은 날짜" 끼리 값이 통째로 같다. 증강 데이터로 보인다.
   → 무작위 분할을 하면 같은 날이 학습과 검증에 동시에 들어가 점수가 부풀려진다
   → 평가는 반드시 고유일만, 분할은 반드시 시간순으로 한다  [6]
   → 학습에는 가중치를 낮춰서 넣는다 (빼면 5월 학습량이 무너진다)  [7-1]

 ── 가동 구조 ──
   휴무일 49일. 휴무일은 전부 일 생산량 0 이고 전력은 기저부하 약 23
   가동일의 전력 구조
     시각별   0 to 7시 야간(중부하) / 8 to 11시·13 to 16시 주간(고부하) / 12시 점심 하락
     요일별   평일 103 to 123 / 토 51 / 일 41
   일 최대가 나는 시각은 8시(29.1%) > 11시(18.9%) > 13시(13.6%) > 9시(11.7%)
   → 상위 4개 시각에 73.3% 가 몰린다

 ── 공휴일은 쉬는 날이 아니다 ──
   2021년 공휴일 10일 중 실제 휴무는 2일뿐이고 그 둘 다 일요일이다.
   나머지 8일은 정상 가동하거나 부분 가동한다.
   → is_holiday 는 그 자체로는 약한 피처다. 추석 대비 보험용으로만 넣었다
   → 부분 가동하는 공휴일(5/5, 5/19, 8/16)이 최대 오차원이다  [8-1]

 ── 생산량과 전력의 관계: 800에서 포화한다 ──
   시간당 생산량   0    1-200  200-400  400-600  600-800
   평균 전력     63.4   103.6   113.7    130.8    145.8
   시간당 생산량  800-1000  1000-1200  1200-1600  1600+
   평균 전력       153.8     156.3      156.6     150.6
   직전 구간 대비   +8.0      +2.5       +0.3      -6.0
   → 800 을 넘으면 더 만들어도 전력이 오르지 않는다. 1600 이상은 오히려 내려간다
   → "생산량을 옮기면 전력이 비례해 따라온다" 는 가정이 이 공장에서는 성립하지 않는다
   → 피크 저감 모형의 결정변수를 생산량으로 두면 안 된다  [9-1]

 ── 기상 ──
   냉방은 22°C 부근에서 시작된다 (cool = max(0, 기온 - 22) 로 반영).
   다만 SHAP 기준 기상의 기여도는 3.3% 로 낮다. 생산량에 가려져 있다  [8-3]

 ── 데이터 품질 문제 ──
   가동중단 20행        is_stop      학습·평가 제외
   시간컬럼 손상 2일    is_corrupt   7/13, 7/15. 학습·평가 제외
   생산기록 누락 15일   is_prod_missing  생산량 0인데 전력은 고부하
                        → 학습에서만 제외 (train_ok_strict), 평가에는 포함  [4]


==============================================================
 [4] 전처리 — 팀원 작업과 내 보강
==============================================================

 팀원(최치훈)이 src/preprocess.py 로 기본 정제를 해뒀다. 모든 분석·학습이
 load() 하나만 부르면 되도록 입구를 하나로 만든 구조가 좋았다.
 나는 거기에 네 가지를 보강했다.

 ── 보강 1. 하루 24행·1시간 연속을 강제로 검사 ──
   문제   전처리가 조용히 깨져도 알 수 없었다. 행이 빠지면 lag 가 통째로 밀린다
   시도   load() 안에 assert 두 개를 넣었다
            하루 24행이 아닌 날이 있으면 즉시 중단
            dt 간격이 1시간이 아니면 즉시 중단
   결과   현재 데이터는 통과한다. 앞으로 데이터가 바뀌면 바로 잡힌다

 ── 보강 2. 공휴일 정보 추가 ──
   문제   달력 피처에 공휴일이 없었다. 추석이 테스트에 들어올 가능성이 있다
   시도   2021년 공휴일(대체공휴일 포함)을 넣고 is_holiday 생성
   결과   공휴일 10일 중 8일이 정상 가동이라 피처 자체의 힘은 약하다.
          그래도 추석 대비 보험으로 남겨 뒀다.
          ★ 이 조사 과정에서 "공장이 공휴일에 쉬지 않는다" 는 것을 알게 됐고,
            그것이 나중에 최대 오차원을 설명하는 열쇠가 됐다  [8-1]

 ── 보강 3. 생산기록 누락일 탐지 (★ 가장 큰 보강) ──
   문제   팀원은 7/13, 7/15 두 날만 손상으로 잡아 뒀다. 그런데 "생산량이 0인데
          전력은 고부하" 인 날이 더 있어 보였다. 이런 날을 학습에 넣으면 모델이
          "생산 0 → 전력 높음" 을 배워서 생산량 피처의 기울기가 눌린다
   시도   일 생산량이 0이면서 휴무일이 아닌 날을 전부 찾았다
   결과   15일이 나왔다 (복제 9일 / 고유 6일). 예상보다 훨씬 많다
            1/1, 1/2, 1/10, 1/24, 2/11, 2/12, 2/13, 3/1, 3/7, 3/14, 3/21, 3/28, 5/9 ...
            이 15일: 생산 기록 0 인데 일 최대전력 평균 157
            나머지 193일: 생산 14,936 / 전력 166
          → is_prod_missing 플래그와 train_ok_strict (학습용 행) 를 만들었다
          → 학습 행 6,100 → 5,788 로 줄었다
          → 평가에서는 빼지 않았다. 테스트에도 이런 날이 올 수 있기 때문이다
   효과   [7-1] 3번 참조. 이 날들을 학습에 넣으면 CORE MAE 가 9.15 → 9.93 으로 나빠진다

 ── 보강 4. 일 단위 집계값을 전처리 단계로 올림 ──
   문제   day_prod 같은 값을 분석 스크립트마다 따로 계산하고 있었다
   시도   preprocess 에서 한 번만 만들어 내려보냈다
   결과   스크립트 간 값이 어긋날 여지가 없어졌다

==============================================================
 [6] 검증 규약 — 세 번 바뀌었다
==============================================================

 이 항목이 이 프로젝트에서 가장 많은 혼선을 만들었다. 경위를 남겨 둔다.

 ── 왜 무작위 분할을 쓰면 안 되나 ──
   257일 중 161일이 복제일이다. 무작위로 나누면 같은 날이 학습과 검증에
   동시에 들어간다. 모델이 답을 외운 상태로 점수를 받는 것이라 의미가 없다.
   → 시간순 롤링 폴드: 각 월을 검증하고, 그 이전 전체를 학습한다
   → 평가는 고유일만. 복제일을 평가에 넣으면 점수가 부풀려진다
   → 평가셋은 어떤 설정에서도 고정한다. 학습 행만 바꾼다
     (설정마다 평가셋이 달라지면 설정 간 비교가 성립하지 않는다)

 ── 규약 변천 ──
   D12  개발 폴드 5 to 9월 전부
   D17  개발 폴드 5 to 8월 / 9월은 미개봉 홀드아웃 (팀원 변경, 내가 맞춤)
   D22  폴드 5 to 9월 전부 / 판단은 CORE(7 to 9월) 기준 / 홀드아웃 없음  ← 현재

 ── D22 가 타당한 이유 ──
   7 to 9월은 전부 고유일이고 테스트 구간(9/15 이후 추정)과 성격이 같다.
   5월은 학습이 4개월뿐인 데다 그 대부분이 복제일이라 오차가 혼자 크다.
     폴드별 MAE (최종 설정)   5월 18.0 / 6월 1.4 / 7월 7.0 / 8월 6.5 / 9월 5.4
   5월을 섞으면 평균이 5월에 끌려간다. 그래서 CORE 를 따로 본다.
   대신 별도 홀드아웃이 없어졌다 → 보고서에 한계로 명시해야 한다

 ── 이것 때문에 생긴 사고 ──
   규약이 바뀔 때마다 이전에 낸 숫자가 전부 무효가 된다.
   실제로 두 번 다시 측정해야 했다 ([7-3]).
   내 8.77 과 팀원 13.9 를 비교했다가 "기준이 달라 비교 불가" 였던 적도 있다.
   ★ 이 문서의 모든 수치는 "어떤 기준에서 잰 것인지" 를 반드시 같이 적었다

   시도    누적 생산량(설비 가열 상태 대리) / 기온 x 생산 / 전날 최고기온(열 축적) /
           최근 4주 같은 시각의 추세 — 4개를 한꺼번에 추가
   결과    MAE 6.508 → 6.594 (악화). peakMAE 만 12.48 → 12.14 로 미세 개선
   해석    이미 들어 있는 피처로 설명되는 정보였다. [10] 2번과 같은 결론이다

 ▷ 3. 타깃·손실을 바꾸면 지표를 맞바꿀 뿐이다
             설정            MAE     RMSE   peakMAE   일최대MAE
             기준           6.508   9.536   12.479    10.93
             로그 타깃       6.379   9.744   13.901    11.83
             Huber 손실      6.953   9.829   11.471    10.98
             분위 0.55      6.681   9.731   11.387    10.19
             잔차 학습       8.320  12.495   14.211    10.91
   ★ 해석  로그 타깃은 MAE 가 가장 낮지만(-0.13) peakMAE 가 13.9 로 나빠진다.
           로그를 씌우면 큰 값의 오차를 덜 벌하니 당연한 결과다.
           요금이 피크로 매겨지는 과제에서 이 맞바꿈은 손해다 → 쓰지 않는다.
           잔차 학습(지난주 값 대비 변화량만 예측)은 MAE 가 크게 나빠졌다.
           다만 일 최대 편향은 +6.81 → +2.90 으로 줄었다 → 아래 5번의 힌트가 됐다

 ▷ 4. ★ 진짜 여유는 "일 최대" 에 있었다
   발견    시간별 MAE 는 6.51 인데 일 최대 MAE 는 10.93 이다. 1.7배다.
           그리고 편향이 +6.80 — 일 최대를 일관되게 6.8 낮게 본다
   원인    모델 성능 문제가 아니라 추정량을 잘못 고른 것이다.
           점 예측은 시각마다 "가운데 값"(조건부 중앙값)을 맞힌다.
           가운데 값 24개의 최대는, 실제 24개 값의 최대보다 구조적으로 낮다.
           실제 값은 위아래로 흔들리므로 그중 최대는 중앙값들의 최대보다 높다.
           → 시간별로 아무리 잘 맞혀도 그 최대를 그대로 쓰면 반드시 낮게 나온다

 ▷ 5. ★ 해법: 일 최대는 분위 0.9 로 추정한다
   시도    분위 수준을 0.75 부터 0.95 까지 올리며 일 최대 추정 성능을 쟀다
             설정        시간별MAE  일최대MAE  일최대편향
             점 예측        6.51     10.93     +6.80
             분위 0.75      9.42      9.97     +3.88
             분위 0.80     10.12      9.39     +2.81
             분위 0.85     12.67      8.82     +1.57
           ★ 분위 0.90     14.67      8.61     -0.16
             분위 0.95     19.40      8.66     -1.90
           전체 5 to 9월에서도 같은 방향이다 (점 예측 12.44/+6.13 → 분위 0.9 10.88/-1.13)
   결과    분위 0.9 에서 일 최대 MAE 10.93 → 8.61 (-21%), 편향 +6.80 → -0.16
           단조롭게 좋아지다가 0.9 에서 편향이 0 을 지난다. 우연이 아니다

   ※ 폴드별로 보면 이득이 고르지 않다 — 숨기지 말 것
             폴드      점예측 MAE/편향     분위0.9 MAE/편향
             2021-05   18.70 / +3.34      20.30 / -5.13   ← 점 예측이 낫다
             2021-07   15.97 / +12.54     11.36 / +4.84   ← 분위가 크게 낫다
             2021-08    7.98 / +3.83       6.65 / -3.24   ← 분위가 낫다
             2021-09    6.63 / +1.24       6.83 / -4.22   ← 거의 같다
           이득의 대부분이 7월에서 나온다. 7월은 점 예측의 편향이 +12.54 로 가장 심한 달이다.
           9월은 두 방법이 사실상 같다. 5월은 점 예측이 낫다.

   그래도 분위 0.9 를 쓰는 이유
     · 편향이 사라진다. 피크 요금 관점에서 "일관되게 낮게 본다" 는 가장 나쁜 성질이다.
       늘 낮게 보면 현장은 끝까지 대비하지 않게 된다
     · 평균적으로 낫고 (CORE 8.61 vs 10.93), 나쁠 때도 크게 나쁘지 않다
     · 경보에 쓰는 모델과 같은 것이라 따로 학습할 필요가 없다 ([9-2])

 ▷ 6. 아직 시도하지 않은 것 (일 단위 전용 모델) — 해봤지만 안 됐다
   시도    타깃을 일 최대로 두고 일 단위 피처(일 생산량·일 최고기온·요일·지난주 일최대 등)
           17개로 별도 모델을 학습
   결과    일 최대 MAE 11.00 / 편향 +5.44 → 현재 방식(10.93)보다 나쁘다
   해석    하루를 한 줄로 요약하면 하루 안의 모양 정보가 사라진다.
           시간별로 예측한 뒤 최대를 취하는 쪽이 정보를 더 쓴다
   보정 계수(학습 구간의 실제/예측 비율을 곱하는 방식)도 시험했으나 과보정됐다 (편향 -8.52)

 ▷ 정리 — 이 단계에서 얻은 것과 포기한 것
   얻은 것  일 최대 추정을 분위 0.9 로 교체. MAE -21%, 편향 제거
            → forecast.py 와 predict_test.py 가 두 값을 함께 출력한다
              일최대_추정(분위 0.9, 권장) / 일최대_점예측(참고)
   포기한 것 앙상블 · 추가 피처 · 로그 타깃 · Huber · 잔차 학습 · 일 단위 전용 모델
            전부 측정해서 기각했다. 시간별 MAE 6.51 은 현재 구조의 한계로 보인다

   ★ 가장 중요한 교훈
     추정량은 용도별로 달라야 한다. 하나의 예측값으로 모든 질문에 답할 수 없다.
       "이 시각 전력이 얼마나 되나"  → 점 예측 (MAE 6.51)
       "오늘 최대가 얼마나 되나"      → 분위 0.9 (일최대 MAE 8.61, 편향 0)
       "오늘 위험한가"               → 분위 0.9 + 임계값 (일 재현율 97.4%)
     이걸 모르고 점 예측 하나로 전부 답하려 했던 것이 일 최대 편향의 원인이었다

 [10] 반복해서 배운 것
==============================================================

 같은 종류의 실수를 여러 번 했다. 보고서의 "한계와 교훈" 에 쓸 수 있고,
 앞으로 작업할 때 먼저 확인할 목록이기도 하다.

 ── 1. 기준이 다르면 결론이 뒤집힌다 (4번 겪음)  ★
   · 내 MAE 8.77 과 팀원 13.9 를 비교했는데, 검증 구간이 달라 애초에 비교 불가였다
   · 복제일 처리: 팀원은 "그대로" 가 최선, 나는 "가중치" 가 최선. 기준 설정이 달랐다
   · Ridge 피크 MAE 12.7: 팀원 기준에서는 최고, 내 기준에서는 최악
   · D24 상관 0.094: 기준 16개 어디서도 재현 안 됨
   → 숫자를 인용할 때는 반드시 "어떤 기준에서" 를 같이 적는다.
     이 문서의 모든 표에 평가 구간·행 수·시드를 붙여 놓은 이유다

 ── 2. 사례가 드문 조건은 피처로 풀리지 않는다 (3번 겪음)  ★
   · 공휴일 상호작용 피처 (H군) → 효과 없음
   · 공휴일 행 가중치 → 오히려 악화
   · 부분가동일 경과시간 피처 (P군) → CORE 에서 효과 없음
   공통점: 학습 구간에 해당 사례가 2 to 3일뿐이다.
   → 없는 정보를 피처 모양만 바꿔서 만들어 낼 수는 없다.
     이런 건 데이터를 더 받거나, 규칙으로 넣거나, 한계로 명시하는 수밖에 없다

 ── 3. 원인 진단을 먼저 검증해야 한다  ★
   피크 과소예측의 원인을 "트리의 외삽 한계" 로 잘못 짚었다.
   그 가설대로 Ridge 를 붙였다가 전부 실패했다.
   실제 원인은 objective='l1' 이 예측을 중앙값으로 당기는 것이었고,
   그걸 알고 나니 피크행 가중치라는 간단한 처방으로 해결됐다.
   → 폴드별 학습최대/예측최대를 직접 찍어 본 것이 전환점이었다.
     가설을 반증할 수 있는 수치를 먼저 찾아야 한다

 ── 4. 성능이 이상하게 좋으면 누수를 의심한다
   no_plan 세트 MAE 13.36 이 이상하게 좋았다. is_off(타깃 유래)가 섞여 있었다.
   고치니 25.32. 거의 두 배였다

 ── 5. 흔들림보다 작은 차이는 차이가 아니다
   5 to 8월 기준에서 35번이 최고로 보였지만, CORE 에서는 32·35·36·39·43 이
   전부 흔들림 안쪽이었다. 28개 중 최저값을 고르는 것은 잡음을 고르는 것에 가깝다.
   → 효과의 실체는 "조합" 이 아니라 "재료"(얕은 나무 + 피크 가중치)였다

 ── 6. 모델이 항상 규칙보다 나은 것은 아니다
   피크 시각 맞히기에서 모델(20.4%)이 "무조건 8시"(24.1%)보다 못했다.
   → 모델을 쓰기 전에 단순 기준선과 비교해야 한다.
     baseline.py 를 계속 돌리는 이유이기도 하다

 ── 7. 도구 문제로 시간을 많이 썼다 (기록용)
   · numpy 2.4.6 의 BLAS(MKL)가 행렬곱에서 인터프리터를 죽였다.
     처음엔 그림 그리는 코드(axvspan)를 의심해 엉뚱한 곳을 고쳤다.
     원인은 np.eye(2) @ np.eye(2) 한 줄로 확인됐고,
     conda install -c conda-forge "libblas=*=*openblas" 로 해결
   · PowerShell 의 Add-Content 가 UTF-8 파일을 ANSI 로 읽어 문서가 깨졌다
     → 이후 문서 수정은 전부 파이썬으로 처리
   ★ 증상이 나는 지점과 원인이 있는 지점이 다를 수 있다.
